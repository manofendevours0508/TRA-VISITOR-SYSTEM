# TRA-DIRECT

Digital Registry Management, Office Directory and Visitor Guidance System for the Tanzania Revenue Authority.

Original proposal: [docs/PROJECT PROPOSAL NEW.docx](docs/PROJECT%20PROPOSAL%20NEW.docx)

## Structure

- `server/` — Express + Prisma API (PostgreSQL)
- `client/` — React (Vite + Tailwind) single-page app with two areas:
  - `/` — public kiosk/directory (unauthenticated)
  - `/staff/*` — internal staff registry portal (authenticated)

## Current scope

Both halves of Phase 1 are implemented:

- **Public Kiosk** — home/search, office & service detail, building map placeholder,
  announcements, QR codes.
- **Staff Registry Portal** — login (JWT), role-based access, incoming/outgoing
  correspondence registers with file upload, document detail with status updates,
  file transfer/tracking between officers, document search, office & service
  directory management, announcements manager, user management (admin), audit log.

Not yet built: the building map is still a placeholder graphic (needs the real
floor plan), and reporting is limited to the dashboard summary tiles (no export yet).

## Running locally

Needs a PostgreSQL database — either a local install or a free cloud instance
(Neon, Supabase, or the same Render Postgres used in production). Put its
connection string in `server/.env` as `DATABASE_URL` (see `.env.example`).

```bash
# API
cd server
npx prisma db push       # creates/updates tables from schema.prisma (first time + after schema changes)
npm run prisma:seed      # first time only (also re-runnable safely)
npm run prisma:sync-translations  # populates Swahili text for the seeded data
npm run dev              # http://localhost:4000 (nodemon, auto-reload)

# Kiosk + staff app
cd client
npm run dev              # http://localhost:5173
```

## Deploying to Render

`render.yaml` at the repo root defines all three pieces as a Render
"Blueprint" — a Postgres database, the API as a Web Service, and the
client as a Static Site.

1. On [render.com](https://render.com), **New +** → **Blueprint** → connect
   this GitHub repo. Render reads `render.yaml` and provisions all three
   resources in one go.
2. The two services cross-reference each other's URL
   (`CLIENT_BASE_URL` on the API, `VITE_API_URL` on the static site) using
   the names in `render.yaml` (`tra-direct-api`, `tra-direct-kiosk`). If
   Render has to rename either service because the name is taken, update
   both env vars in the Render dashboard to match the real assigned URLs,
   then redeploy.
3. Once the API service is live, open its **Shell** tab (in the Render
   dashboard) and run the one-off seed commands:
   ```bash
   npm run prisma:seed
   npm run prisma:sync-translations
   ```
4. `JWT_SECRET` is auto-generated by the blueprint; `DATABASE_URL` is
   wired automatically from the Postgres resource.

**Free-tier caveats**: the free Postgres instance expires after 90 days
unless upgraded, and the free Web Service spins down after inactivity
(the first request after idling will be slow while it wakes up). Fine for
testing/demo; upgrade both before relying on this for a real kiosk.

### Windows path note

This project's path contains `&` (`CODES&PROJECTS`), which breaks `npm.cmd`/`npx.cmd`
batch-file argument parsing on Windows. If you see `Cannot find module 'C:\...\index.js'`
errors when running `npm run ...` or `npx ...` directly from a shell, invoke the tool's
JS entry point with `node` instead, e.g.:

```bash
node node_modules/prisma/build/index.js migrate dev
node node_modules/vite/bin/vite.js --host
```

The `npm run dev` scripts inside `server/package.json` work fine since they're
launched by npm itself once already running; it's ad-hoc `npx <tool>` invocations
from an external shell that are affected.
